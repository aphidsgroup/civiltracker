# Production Migration Reconciliation — Operator Packet

**Release candidate:** `76b232c` (branch `fix/project-checklist-tenant-authorization`)
**Scope:** Reconcile the production Prisma migration ledger with the repository, then apply pending migrations, then ship code.
**This packet is credential-free.** Every command below uses placeholders. Never paste connection URLs, passwords, tokens or `.env` contents into this document, tickets, chat, PRs or evidence files.

Related: `docs/BUILD_AND_DB_DEPLOYMENT_POLICY.md` (build-only Vercel builds; known `P3009` on `20260625160000_phase_9_multitenant`), `docs/production-migration-audit.md`, `docs/rollback-plan-phase-7.md`.

---

## 0. Hard stop condition

**STOP and escalate — do not run `migrate resolve`, `migrate deploy`, `db push`, any hand-written DDL, merge or deploy — if any of the following is true:**

- Any ledger row is in a state other than the expected ones in §2 (e.g. an unexpected failed row, a row for a migration not in the repo, a checksum mismatch on an applied migration).
- The drift comparison (§4) yields any **Class C** or **Class D** item.
- A verified backup / restore point (§5) or a successful clone dry-run (§6) is missing.
- Any required approval in §8 is missing, or the change window has closed.
- Anyone proposes executing `prisma/migration_diff.sql` (see §1).
- Any step would require writing a secret into a file, log or command history.

A stop is not a failure. Record what was observed and hand back to the approvers.

## 1. `prisma/migration_diff.sql` — review-only, never execute

- The file is **UTF-16 LE with CRLF line endings**, not a migration and not tracked by Prisma's ledger.
- It contains **destructive-looking DDL** (drop/alter statements generated by a schema diff). It reflects a diff between two states at some point in time, not a reviewed change.
- It is a **reference artifact for the drift review only**. It must **never** be executed against any database — production, clone, or staging — by `psql`, `prisma db execute`, a GUI client, or by copying fragments.
- If you need to read it, convert a local copy to UTF-8 for viewing (e.g. `iconv -f UTF-16LE -t UTF-8 <file> > <local-view-copy>`); do not commit the converted copy.

## 3. Evidence step A — read-only migration ledger

Run as a **read-only role** against production. Capture **status fields only** — no data rows from app tables.

```sql
-- placeholder: run via <READ_ONLY_SQL_CLIENT> connected with <PROD_READONLY_CONNECTION_REF>
SELECT migration_name,
       started_at,
       finished_at,
       rolled_back_at,
       applied_steps_count,
       (logs IS NOT NULL) AS has_logs,
       checksum
FROM "_prisma_migrations"
ORDER BY started_at;
```

And the Prisma view (read-only; does not modify anything):

```
<PRISMA_CLI> migrate status --schema prisma/schema.prisma   # env: DATABASE_URL=<PROD_READONLY_CONNECTION_REF>
```

Classify every row:

| Ledger state | Meaning | Action |
|---|---|---|
| `finished_at` set, `rolled_back_at` null | applied | compare checksum to repo file |
| `finished_at` null, `rolled_back_at` null | **failed** | reconciliation candidate (§7) |
| `rolled_back_at` set | resolved as rolled back | confirm a later successful row exists or it is pending |
| repo migration with no row | pending | will be applied by `migrate deploy` |
| row with no repo migration | **unknown** | **hard stop** |

Do not copy the `logs` column text into evidence if it contains connection details; note only `has_logs` and a redacted summary.

## 4. Evidence step B — schema inventory and drift classification

Read-only `information_schema` / `pg_catalog` queries against production (and later the clone), exported as sorted text for diffing. Placeholders only:

```sql
-- Tables
SELECT table_name FROM information_schema.tables
 WHERE table_schema = '<APP_SCHEMA>' AND table_type = 'BASE TABLE' ORDER BY 1;

-- Columns (name, type, nullability, default)
SELECT table_name, column_name, data_type, udt_name, is_nullable, column_default
  FROM information_schema.columns WHERE table_schema = '<APP_SCHEMA>' ORDER BY 1, 2;

-- Enums and their values
SELECT t.typname, e.enumlabel, e.enumsortorder
  FROM pg_type t JOIN pg_enum e ON e.enumtypid = t.oid
  JOIN pg_namespace n ON n.oid = t.typnamespace
 WHERE n.nspname = '<APP_SCHEMA>' ORDER BY 1, 3;

-- Indexes (including unique)
SELECT tablename, indexname, indexdef FROM pg_indexes
 WHERE schemaname = '<APP_SCHEMA>' ORDER BY 1, 2;

-- Foreign keys (with ON DELETE rule)
SELECT tc.table_name, tc.constraint_name, kcu.column_name,
       ccu.table_name AS ref_table, ccu.column_name AS ref_column, rc.delete_rule
  FROM information_schema.table_constraints tc
  JOIN information_schema.key_column_usage kcu USING (constraint_schema, constraint_name)
  JOIN information_schema.constraint_column_usage ccu USING (constraint_schema, constraint_name)
  JOIN information_schema.referential_constraints rc USING (constraint_schema, constraint_name)
 WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = '<APP_SCHEMA>' ORDER BY 1, 2;
```

**MediaAsset claim fields** — record explicitly (expected **absent** before migration 7, **present and nullable** after):

```sql
SELECT column_name, data_type, is_nullable
  FROM information_schema.columns
 WHERE table_schema = '<APP_SCHEMA>' AND table_name = 'MediaAsset'
   AND column_name IN ('consumedAt', 'consumedBy', 'consumedRecordId');
-- Also confirm existence of: to_regclass('"MediaAsset"'), '"SitePhoto"', '"BillAttachment"'
-- (these tables were created outside tracked history via db push; the migration guards on them).
```

Expected target types: `consumedAt TIMESTAMP(3) NULL`, `consumedBy TEXT NULL`, `consumedRecordId TEXT NULL`.

Generate the repo-side expectation offline (no DB connection) and diff:

```
<PRISMA_CLI> migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > <LOCAL_EXPECTED_DDL>   # review only, never execute
```

**Drift classes** — every difference must be assigned exactly one:

| Class | Description | Example | Outcome |
|---|---|---|---|
| **A — Expected pending** | Objects added by a pending migration | 3 MediaAsset claim columns absent | OK; `migrate deploy` will add |
| **B — Present, ledger lagging** | Objects exist but migration row failed/missing | phase 9 columns present, row `P3009` | Reconcile via `migrate resolve` (§7), with approval |
| **C — Extra in production** | Table/column/index/enum value/FK in prod not in schema | object created by hand or `db push` | **Hard stop** — never drop; needs design decision |
| **D — Conflicting** | Same object, different type/nullability/default/enum set/FK rule, or missing without a pending migration | `Company.plan` wrong type, missing FK | **Hard stop** |

Note: `migration_diff.sql` and `<LOCAL_EXPECTED_DDL>` may show drops for Class C items. That is exactly why neither may be executed.

## 7. Reconciliation (production, after approval gate 1)

For each **Class B** failed row only, and only when the clone proved its objects are fully present:

```
<PRISMA_CLI> migrate resolve --applied <MIGRATION_NAME>      # env: DATABASE_URL=<PROD_MIGRATOR_CONNECTION_REF>
```

If a failed migration's objects are **not** fully present, do not mark it applied; stop and escalate (Class D).
Never use `migrate reset`, `db push`, `--accept-data-loss`, or hand DDL on production.

Re-run §3; the ledger must show no failed rows and only Class A pending migrations.

## 8. Approval boundaries (strict order)

Each gate needs a recorded sign-off (name, UTC time, evidence links). Approval of one gate does not carry to the next.

| Gate | Action authorised | Preconditions |
|---|---|---|
| **1 — Reconciliation** | `migrate resolve` on listed Class B rows only | §3–§6 evidence complete; zero Class C/D; backup + restore point verified; window open |
| **2 — Migrate deploy** | `<PRISMA_CLI> migrate deploy` on production (explicit operator action, not in Vercel build) | Gate 1 done; post-resolve ledger clean; `migrate status` shows only expected pending |
| **3 — Merge / deploy** | Merge RC `76b232c` to `main`; production deploy (build-only: `prisma generate && next build`) | Gate 2 done; post-deploy inventory shows MediaAsset claim columns present; clone smoke passed |

Code that reads/writes the claim columns must **not** reach production before Gate 2 completes.
